# Department Lead authentication
No new role or database migration. Department Lead is the existing Department.leadUserId appointment. An active Employee leading an active department in their own OFFICE branch (or legacy HEAD_OFFICE) may authenticate. STORE employees never gain login rights from leadership. Other login roles retain their existing permissions.
- In Administration > Departments choose an active lead from the same branch. In Administration > Users open the employee and choose Set / activate password, provide the administrative reason, then use the one-time link. No direct credential creation or password email. Existing valid credentials are usable; revoked credentials require activation/reset.
- A lead with role Employee receives only effective approvals.request permission (not a change to the persisted role). The Overview shows active members and current assigned resources for departments led; approval beneficiaries are restricted to these departments. Existing reviewer and administrative roles remain unchanged; no new review rights are conferred by the appointment.
- Losing the last active qualifying appointment invalidates sessions, pending invitations and credentials. Department changes are already recorded in the security audit. No automatic change to existing users' roles.
- Administration uses its own vertically scrolling content pane and reference-counted dialog scroll lock.
- Run typecheck, build and the isolated CI integration suite. Do not run CI fixtures on populated staging DB. Manually test employee activation, login, scope, removal, store manager login and all Administration tabs including opening/closing dialogs and scrolling to the bottom.
